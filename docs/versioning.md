# DeepCore-Code 版本号与版本日志规范（落地文档）

> 本文件是版本管理的**唯一权威规范**：四段式版本号 x.x.x.x + 三份版本日志（用户 / 开发者 / AI）。
> 相关约束见 `AGENTS.md`（版本号规范 / 发版流程 / 资产同步纪律）与 `docs/sop/10-release.md`。

---

## 1. 版本号规则（四段式 x.x.x.x）

### 1.1 格式

- **正式版 / 预发行版**：`vA.B.C.D`（如 `v0.0.0.1`）或 `vA.B.C.D-rcN`（如 `v0.0.0.1-rc1`），N 为自然数。
- **单段上限 999**，整体最高 `999.999.999.999`。
- **dev 构建**（tag 之后的未发提交）：`A.B.C.D[-rcN]-dev.<提交数>+<hash>`，由 `app/build.gradle.kts` 的 `gitVersionName()` 自动推导，**不手写**。
- **唯一事实源**：Git Tag / Commit。代码内不写死正式版本号，仅定义 dev 基线 `BASE_VERSION`（见 `build.gradle.kts`）。

### 1.2 里程碑与本仓迭代基线

本仓库从 **`0.0.0.1`** 重新开始迭代：

| 里程碑 | 版本号 | 含义 |
|---|---|---|
| 起点 | `0.0.0.1` | 首个正式号（D=1） |
| 功能跨度 | `0.0.0.10` | 新增/删除功能后正式发版（D 段 +10） |
| 框架跨度 | `0.0.1.0` | 框架重构后正式发版（C 段 +1，**D 段归零**） |

### 1.3 各段语义

| 段 | 所在位 | 触发条件 | 示例变化 |
|---|---|---|---|
| A | 第 1 位 | 颠覆性 / 不兼容里程碑（当前为 0，预留） | — |
| B | 第 2 位 | 更高一级框架 / 结构性变更（当前为 0，预留） | — |
| C | 第 3 位 | **框架级重构**：+1，且 **D 段归零** | `0.0.0.10` → `0.0.1.0` |
| D | 第 4 位 | **功能迭代**：新增 / 删除功能后正式发版时 +10 | `0.0.0.1` → `0.0.0.10` |

### 1.4 迭代规则

| 变更类型 | 版本动作 | 示例 |
|---|---|---|
| 修复 Bug 再发版 | **仅迭代 rc 后缀**，发预发行版 | `v0.0.0.1-rc1` → `v0.0.0.1-rc2` |
| 新增 / 删除功能（正式版） | D 段 +10（0.0.0.10 跨度），**维护者明确**后执行 | `v0.0.0.1` → `v0.0.0.10` |
| 框架重构（正式版） | C 段 +1 且 D 段归零（0.0.1.0 跨度），**维护者明确**后执行 | `v0.0.0.10` → `v0.0.1.0` |
| 首个正式版 | D 段 = 1 | `v0.0.0.1` |

- **约束**：只有维护者明确「发行正式版」才推进 C / D 段；日常 bug 修复一律只在 rc 后缀上迭代，不推进正式档位。
- **驱动方式**：版本号推进只发生在**打 tag 时**，由维护者按上表执行；构建侧（`gitVersionName()`）只负责正确解析任意四段 tag。

> 与 SemVer 关系：`x.x.x.x` 是 SemVer 三段式的本地扩展，语义对齐——bug 修复（.Z）、功能新增（.Y→D+10）、不兼容/重构（.X→C/D 重置），并叠加 rc 预发行标记。

## 2. 三份版本日志

按**受众**拆分三份，各自独立维护、发版前同步更新，三份都应覆盖本次发版内容才可打 Tag。

### 2.1 用户日志（给用户看）

- **位置**：仓库根 `CHANGELOG.md`
- **规范**：Keep a Changelog 风格——倒序（最新置顶）、ISO 8601 日期（YYYY-MM-DD）、顶部 `[Unreleased]`。
- **六类（固定顺序）**：`Added 新增 / Improved 改进 / Fixed 修复 / Changed 变更 / Removed 删除 / Adjusted 调整`。
- **内容**：只写**用户可感知**的变更，措辞用户向（说症状与价值，不说内部实现 / 类名 / 迁移细节）；内部实现不进本文档。
- **责任**：发版必更。初稿从 `git log <prev-tag>..<tag>`（Conventional Commits）汇总后人工润色。

### 2.2 开发者日志（给项目开发者看）

- **位置**：各模块 `docs/modules/<module>.md` 末尾「## 7. 版本演进记录」（一个模块一份）
- **规范**：**叙述式、开发维度**演进；发版前由开发者对本次有改动的模块逐个追加该版条目（版本 + 日期）。
- **内容**：用户日志不展开的内部细节都在这——模块 / 类 / 接口变化、数据结构与 schema 演进、迁移、构建与 CI 变化、关键修复、回滚注意点。
- **责任**：有改动的模块必更；由 pre-commit 校验「模块 ↔ 文档」一一对应。

### 2.3 AI 协同日志（给协同 AI 模型看）

- **位置**：`app/src/main/assets/prompts/90-version-log.md`（随 prompt 资产常驻，AI 运行时可见，属「AI 工作流相关改动」资产）
- **规范**：**结构化、可解析**——为模型消费优化，字段化记录（版本号 / 类型 / 影响面 / 动作要点 / 兼容性·迁移提示），避免散文；成本敏感时保持简短但字段齐全。
- **内容**：AI 据此做任务编排所需的信息——工具新增 / 改动 / 签名变化、schema 与接口演进、提示词 / 技能 / 规则新增、行为迁移与回滚基线。
- **责任**：任何 AI 工作流相关改动（工具增删改、agent 行为、prompt 逻辑）发版时必须同步更新（见 `AGENTS.md` 资产同步纪律）。

## 3. 发版联动与权威链

- **规则权威来源**：本文件（版本规则）→ `AGENTS.md`（纪律）→ `docs/sop/10-release.md`（操作 SOP）。
- **发版顺序**：确认改动面 → 同步 用户 / 开发者 / AI 三份日志 → 在 `main` 打 Tag（如 `v0.0.0.1-rc1`）→ 推送触发 CI → 真机验证三条主线 → 转正式（维护者明确时推进 C/D 档位）。
- **RC 判定**：含新功能、行为变化、构建链路 / 启动 / 容器改动 → 先发 RC；仅纯 bug 修复且不触碰启动 / 容器 → 可直接正式。
