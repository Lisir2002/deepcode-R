# SOP-10 发版（Release）

> 权威源：`AGENTS.md`「发版流程（RC 判定）」+「版本号规范」。发版靠 Git Tag 驱动，**无需手写版本号**。

## 1. 判定是否需要先发 RC

- **操作**：按本发版周期改动面判定。
- **判定**：
  - 含新功能 / 行为变化（定档 `x.Y.0`）→ 必须先发 RC；
  - 仅纯文档 / typo / 资源文案（定档 `x.y.Z`）→ 可直接发正式；
  - 仅纯 bug 修复（定档 `x.y.Z`）→ 小改直接正式，触碰启动/容器的仍先 RC；
  - 构建链路 / 签名 / ABI 打包策略 / CI 改动，或容器镜像 / PRoot 相关改动 → 必须先发 RC。
- **产出**：得出「先发 RC」或「直接发正式」结论，记录到版本档位。

## 2. 确保代码在 main 主线上

- **操作**：所有功能/修补先合并到 `main` 分支，确认在 `main` 最新提交节点上。
- **判定**：`git log --oneline -1` 位于 `main`；严禁在功能分支（`feat/*` / `refactor/*`）上打 Tag。
- **产出**：处于 main 且无未合并分支；出错则先完成合并再继续。

## 3. 维护版本日志（发版必做）

- **操作**：打 Tag 前先更新两部分版本日志（见 `AGENTS.md`「发版流程 → 版本日志（发版必做）」）。
- **判定**：
  1. 仓库根 `CHANGELOG.md`（发布视角）：按 Keep a Changelog 记录本次版本用户可见变更（`Added/Changed/Fixed/Removed`）；初稿从 `git log <prev-tag>..<tag>`（Conventional Commits）汇总后人工润色；仅当无任何用户可见变更时才可跳过。
  2. 本次有改动的各模块文档 `docs/modules/<module>.md` 末尾「## 7. 版本演进记录」追加本次版本开发维度演进。
- **产出**：版本日志与本次发版内容一致，随代码一起在 main 上提交。

## 4. 打 Tag 并推送

- **操作**：在 `main` 最新提交节点打 Tag（如 `v1.7.0-rc1` 或 `v1.7.0`）并推送。
- **判定**：Tag 名格式 `v<主>.<次>.<补丁>[-rc<n>]`；`git push origin <tag>` 成功。
- **产出**：CI 捕获 `v*` Tag 自动构建 Release；推送失败则检查远端权限/网络后重试。

## 5. 实时监控与产物校验

- **操作**：按 `docs/ci-release.md` 云端构建运维手册实时监控 CI 全流程（6 阶段）。
- **判定**：产物清单校验通过（双 ABI 通用包 arm64-v8a + x86_64、签名正确、版本号与 Tag 匹配）。
- **产出**：Release 产物就绪；若产物校验失败按手册回退/排查。

## 6. RC 包真机验证 / 热修复 / 转正

- **操作**：真机装 rc 包，至少跑通 AI 对话 + 终端 + 容器启动三条主线。
- **判定**：
  - 有问题 → 从该 RC Tag 拉 `hotfix/xxx` 分支修复（**勿从最新 main 拉**），升 rc 序号打 Tag 重发，修复合回 main 并删除 hotfix 分支；
  - 无问题 → 直接打正式 Tag（`v1.7.0`）推远端转正。
- **产出**：正式版发布或 rc<n+1> 修复版发出；出错按热修复流程处理。
